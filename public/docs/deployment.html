Production · Déploiement

Déploiement

Agent BI se déploie en deux conteneurs : api (FastAPI + agents) et web (Nginx + front statique). SQL Server peut être externe (Azure SQL recommandé) ou conteneurisé pour les environnements de dev.

Topologie de référence

  • Reverse proxy : Nginx (TLS, HSTS, compression, cache statique).
  • Web : Nginx servant dist/ généré par Vite.
  • API : uvicorn (--workers 2 minimum) derrière le proxy.
  • Base : SQL Server managé (Azure SQL DB, RDS SQL Server, etc.).
  • Observabilité : Prometheus scrape /metrics ; Grafana pour les dashboards.

Docker Compose (démarrage rapide)

# docker-compose.yml (extrait)
services:
  api:
    build: ./api
    env_file: .env.deploy
    ports: ["8000:8000"]
    volumes:
      - agentbi_uploads:/data/uploads
    restart: unless-stopped

  web:
    build: ./
    ports: ["80:80"]
    depends_on: [api]
    restart: unless-stopped

volumes:
  agentbi_uploads:

Commande de lancement :

docker compose --env-file .env.deploy up --build -d
docker compose logs -f api
Builds multi-étapes. Le Dockerfile du front est multi-stage : étape builder (Node 20 → npm run build), étape runtime (Nginx copie dist/). L'image finale pèse ~40 Mo.

Nginx : proxy & SSE

Attention au buffering : désactivez-le sur la route SSE, sinon les événements arrivent en paquets tardifs.

location /api/pipeline-stream {
  proxy_pass http://api:8000;
  proxy_http_version 1.1;
  proxy_set_header Connection "";
  proxy_buffering off;
  proxy_cache off;
  proxy_read_timeout 3600s;
}

Kubernetes (résumé)

  • 1 Deployment pour l'API (replicas: 2, HPA sur CPU et RPS).
  • 1 Deployment pour le web (statique, replicas: 2).
  • Service ClusterIP + Ingress (NGINX / Traefik) avec sticky sessions pour SSE.
  • Secrets montés via External Secrets Operator ou CSI driver.
  • ConfigMap pour les paramètres non sensibles.

Mises à jour (zero-downtime)

  1. Build des nouvelles images avec tag vX.Y.Z.
  2. Rolling update côté API (maxSurge: 1, maxUnavailable: 0).
  3. Le web est invalidé côté CDN après déploiement.
  4. Vérification via /api/health et /api/version.

CI/CD

Le workflow GitHub Actions (.github/workflows/ci.yml) lance :

  • Python : pytest, mypy, ruff.
  • Node : npm run build, npm test, eslint.
  • Docker : buildx multi-arch, push sur GHCR.

Sauvegarde & restauration

Planifiez au moins une sauvegarde complète quotidienne + journaux des transactions toutes les 15 min. Testez la restauration sur un environnement de staging chaque trimestre — une sauvegarde non testée n'existe pas.

RTO & RPO. À moins d'exigences particulières, viser RTO < 1 h et RPO < 15 min couvre la majorité des besoins BI.
