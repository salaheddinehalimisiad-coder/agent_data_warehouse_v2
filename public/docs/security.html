Production · Sécurité

Sécurité

Agent BI manipule potentiellement des données sensibles. Nous appliquons une défense en profondeur : authentification, autorisation, isolation, journalisation, et traitement prudent des payloads LLM.

Authentification

L'authentification repose sur JWT signés HS256. Les mots de passe sont stockés avec bcrypt (coût 12). Les tokens portent iss=agent-bi et expirent après 24 h par défaut. Un refresh token optionnel peut être activé côté serveur pour prolonger la session sans re-login.

Changer les secrets. Le JWT_SECRET fourni dans .env.example est un placeholder. En production, utilisez au minimum 32 octets aléatoires (openssl rand -hex 32) et stockez-le dans un secret manager (AWS Secrets Manager, Azure Key Vault, Doppler…).

Autorisation (RBAC)

Trois rôles par défaut : viewer (consultation), analyst (lancer des pipelines, NL→SQL), admin (gestion des utilisateurs, exports, secrets). Les endpoints critiques sont protégés par dépendance FastAPI :

@router.post("/api/export/{format}")
def export(format: str, user: User = Depends(require_role("analyst"))):
    ...

Protection des données

  • Masquage PII. Le Sécurisateur applique des règles regex (emails, téléphones, numéros de carte) ; les valeurs sensibles ne sont jamais envoyées au LLM.
  • Chiffrement au repos. SQL Server TDE activable ; fichiers uploadés stockés dans un volume chiffré.
  • Chiffrement en transit. Nginx termine TLS 1.3 ; HSTS 1 an ; cookies Secure + SameSite=Lax.
  • Anonymisation. Un mode démo hashe automatiquement les colonnes détectées comme PII lors des exports.

Prompt injection & LLM safety

Les agents reçoivent leurs instructions depuis des fichiers de prompt versionnés et non modifiables via l'UI. Les données utilisateur sont envoyées en content, jamais en instructions. Un validateur post-LLM vérifie :

  • que le SQL généré ne contient pas DROP, TRUNCATE, DELETE sans clause ;
  • que les identifiants cités existent réellement dans le schéma ;
  • que les quantificateurs restent dans les bornes (LIMIT 10 000 max par défaut).
Liste blanche. En option, vous pouvez restreindre le SQL généré à un ensemble de vues pré-autorisées, ce qui neutralise la quasi-totalité des risques d'injection.

Journalisation & audit

Chaque appel API est journalisé avec session_id, user_id, endpoint, status, duration_ms. Les logs sont au format JSON pour être ingérés par ELK / Loki / Datadog. L'historien conserve la lignée des données : on sait, pour chaque colonne du DW, d'où elle vient et quelles transformations elle a subies.

Rate limiting

Par IP et par utilisateur : 60 rps en steady state, burst à 120. Les endpoints coûteux (/api/query, /api/export/*) ont leur propre quota (10 requêtes/minute). Dépassement → 429 Too Many Requests.

CORS

La configuration CORS par défaut n'autorise que les origines listées dans CORS_ORIGINS (allowlist). Les requêtes OPTIONS sont traitées par FastAPI ; aucun wildcard * en production.

Conformité

  • RGPD. Endpoint DELETE /api/users/me pour la suppression définitive des données utilisateur (droit à l'effacement).
  • SOC 2 friendly. Logs immuables, contrôle d'accès, sauvegardes chiffrées, rotation des secrets documentée.

Check-list avant production

  1. Remplacer JWT_SECRET et tous les secrets du .env.
  2. Activer HTTPS (certificat valide + redirection 80 → 443).
  3. Configurer un backup automatique de la base (au moins quotidien, rétention 30 j).
  4. Restreindre les IP d'admin (VPN ou allowlist réseau).
  5. Monter un tableau de bord d'observabilité (Grafana + alertes).
  6. Tester la restauration à partir d'une sauvegarde.
