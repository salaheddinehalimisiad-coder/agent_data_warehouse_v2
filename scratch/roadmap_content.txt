


ANTIGRAVITY BI
Agent-Assisted Data Warehouse Design & ETL Automation



1. Vision & Problème à Résoudre
1.1 Le Problème Central
Construire un Data Warehouse depuis une base OLTP existante est un processus coûteux en temps et expertise. Il implique : analyse du schéma source, conception du modèle dimensionnel (Kimball), écriture du DDL, ETL complet avec gestion des Slowly Changing Dimensions, et génération de requêtes analytiques (SQL OLAP, MDX, DAX). Ce processus prend des heures ou des jours selon la complexité de la base source.
Ce projet automatise l'INTÉGRALITÉ de ce pipeline grâce à des agents IA orchestrés par LangGraph.


1.2 Ce que veut l'utilisateur
L'utilisateur — un data engineer, un étudiant, ou un analyste — doit pouvoir :
Uploader son fichier source (.bak SQL Server, .csv, ou connexion SQL directe)
Lancer l'agent et observer le pipeline s'exécuter en temps réel via SSE
Valider ou modifier le modèle dimensionnel proposé via une interface de chat
Obtenir un Data Warehouse opérationnel sur SQL Server avec Star Schema ou Constellation
Recevoir automatiquement les requêtes analytiques adaptées à SON schéma généré
Télécharger un rapport PDF professionnel documentant tout le processus

3.3 Comment le Modeler Fonctionne (Algorithme Générique)
Le nœud modeler.py doit appliquer cet algorithme sur N'IMPORTE quel schéma source :
Étape 1 : Scoring des Tables
Pour chaque table T dans source_metadata, calculer un score de 'fact-ness' :
score(T) = 0
score += 3  si T a >= 2 FK vers d'autres tables
score += 2  si T a des colonnes numériques continues (amounts, quantities, prices)
score += 2  si cardinalité(T) > moyenne des cardinalités
score += 1  si T a des colonnes de date
score -= 2  si T a peu de colonnes (< 5) → probablement une table de référence
score -= 1  si T a une FK qui pointe VERS elle-même (self-join → dimension hiérarchique)
La/les tables avec le score le plus élevé deviennent les tables de faits candidates.

Étape 2 : Détection des Dimensions
Pour chaque table D référencée par une FK depuis une table de faits F :
D devient une dimension candidate
Vérifier si D est également une table de faits (constellation) → si oui, créer 2 measure groups
Vérifier la profondeur de la chaîne FK : D1 → D2 → D3 → snowflake → dénormaliser en étoile
Détecter les self-joins dans D → dimension récursive (hiérarchie employé/manager)

Étape 3 : Génération de DimDate
DimDate est TOUJOURS générée algorithmiquement (elle n'existe pas dans la source OLTP). L'algorithme :
Scanner toutes les colonnes de type DATE/DATETIME dans toutes les tables
Regrouper par contexte sémantique (même table → rôles multiples possibles)
Générer une DimDate unique avec attributs standard : DateKey, FullDate, Day, DayName, Week, Month, MonthName, Quarter, Semester, Year
Si plusieurs colonnes date sur la même table de faits → role-playing dimensions (DateKey, DueDateKey, ShippedDateKey...)

Étape 4 : Génération des Mesures
Pour la table de faits F, détecter les mesures candidates :
Colonnes numériques NON-clé → mesures additives (SUM)
Colonnes de type MONEY/DECIMAL → mesures financières (SUM + AVG)
Colonnes de type INT petites valeurs → mesures semi-additives (AVG par certaines dimensions)
Mesures calculées automatiques : si colonnes 'price' et 'quantity' détectées → proposer une mesure Amount = price × quantity

P3-02 : Query Generator — Générique sur Tout Schéma
Fichier : nodes/query_generator.py (NOUVEAU)
Ce nœud est le plus représentatif de la genericité. Il doit générer des requêtes analytiques ADAPTÉES au schéma DW que le Modeler a produit, sans aucune connaissance préalable de ce schéma.

Algorithme de génération générique :
Lire state['logical_model'] pour extraire : nom de la table de faits, liste des dimensions, liste des mesures avec leurs types
Pour chaque mesure numérique détectée → générer une requête SUM / AVG par dimension
Pour chaque dimension avec des colonnes de date → générer des requêtes temporelles (YTD, par année, par mois)
Pour chaque dimension avec une hiérarchie détectée → générer un ROLLUP sur cette hiérarchie
Pour toutes les mesures → générer ROW_NUMBER / RANK / DENSE_RANK partitionnés par chaque dimension
Pour les mesures financières → générer LAG/LEAD pour comparaison période précédente

Structure du prompt LLM pour la génération :
Le prompt injecte le schéma DW généré, pas un schéma fixe. Exemple de structure :
SYSTEM PROMPT :
Tu es un expert SQL Server / OLAP. Génère des requêtes analytiques adaptées à CE schéma spécifique.

CONTEXTE SCHÉMA (dynamique, injecté depuis state['logical_model']) :
- Table de faits : {fact_table_name}
- Mesures : {measures_list}  (ex: [TotalAmount, Quantity, UnitPrice])
- Dimensions : {dimensions_list}  (ex: [DimDate, DimProduct, DimCustomer])
- Hiérarchies détectées : {hierarchies}
- Colonnes date : {date_columns}

INSTRUCTIONS :
1. Génère 3 requêtes SQL analytiques avec Window Functions
2. Génère 1 requête ROLLUP sur la première dimension hiérarchique trouvée
3. Génère 1 requête CUBE sur les 2 premières dimensions
4. Si SSAS est disponible, génère 3 requêtes MDX adaptées
5. Si modèle tabulaire disponible, génère 5 mesures DAX adaptées
RETOURNE : JSON avec clés 'sql_olap', 'mdx', 'dax'


Exécution et collecte des résultats :
Après génération, le nœud exécute les requêtes SQL analytiques directement sur le DW via SQLAlchemy et stocke les résultats dans state['query_results']. Les requêtes MDX/DAX sont incluses dans le rapport mais non exécutées (elles nécessitent SSAS).

P3-05 : CDC Watermark — ETL Incrémental
Fichier : nodes/cdc_watermark.py (NOUVEAU)
Actuellement, chaque run fait un Full Load. Pour les grandes bases, cela n'est pas acceptable. Implémenter un mécanisme de watermark générique :
Créer outputs/etl_watermarks.json pour persister les timestamps par table
Au démarrage, lire le watermark et déterminer le mode : full_load (premier run ou reset) vs incremental
En mode incrémental, extraire seulement WHERE last_modified_column > watermark
Après chargement réussi, mettre à jour le watermark avec le timestamp du run
Stocker state['etl_mode'] et state['etl_watermarks'] pour transmission au rapport

Défi générique : détecter la colonne de modification
Le framework ne connaît pas à l'avance la colonne qui indique la dernière modification. Algorithme de détection :
# Par ordre de priorité :
1. Colonne nommée 'UpdatedAt', 'ModifiedAt', 'LastModified', 'UpdateDate'
2. Colonne nommée 'CreatedAt', 'InsertedAt', 'CreatedDate' (pour inserts seulement)
3. Colonne auto-increment PK (pour inserts seulement, si pas de colonne date)
4. Fallback : full_load (pas de colonne de tracking disponible)
